# 群管理（企业微信外部群 / 患者绑定 / 群发推送）设计文档

- 日期：2026-09-01
- 状态：待评审
- 关联需求：查询企业微信所有外部群 → 每群关联一位患者 → 可向群推送信息

---

## 1. 背景与目标

### 1.1 背景

随访与健康宣教场景中，医生会把患者拉进企业微信「客户群」（外部群）。当前工作台没有群管理能力：群列表要登录企微管理后台查看，群与患者的关系只存在于医生记忆里，推送消息只能人工在企微里逐个操作。这些信息散落在系统之外，既低效也无法追溯。

### 1.2 目标

1. **群清单**：在页面查看企业微信全部外部客户群（群名、群主、成员数、跟进状态），数据来源为企微真实接口，支持定时自动同步 + 手动立即同步。
2. **患者绑定**：把一个群关联到一位患者（手动绑定 / 换绑 / 解绑）。
3. **群发推送**：选择群与消息类型（文本 / 链接卡片）提交企业群发任务，并在页面查看推送记录与发送结果。

### 1.3 非目标（本期不做）

- 不做 Webhook 群机器人通道（每群需人工建机器人，无法批量维护）；架构预留，不实现。
- 不做患者档案后端化（患者数据目前是前端 mock，见 §4.4）。
- 不做图片 / 视频 / 文件 / 小程序等富媒体推送（企微已支持，本期仅做文本与链接卡片）。
- 不做员工（群主）管理、标签管理、客户管理。
- 不做群成员的逐人档案与会话存档。

## 3. 企业微信接口事实（已核实官方文档）

> 本节结论来自企业微信开发者中心文档（2025-11-17 / 2025-01-13 版本），是设计的硬约束。

### 3.1 access_token

`GET https://qyapi.weixin.qq.com/cgi-bin/gettoken?corpid=ID&corpsecret=SECRET`
有效期 7200s，需缓存与提前续期。

### 3.2 获取客户群列表 `externalcontact/groupchat/list`

- 请求：`{status_filter, owner_filter:{userid_list}, cursor, limit}`
- `status_filter`：`0` 全部（默认）/ `1` 离职待继承 / `2` 离职继承中 / `3` 离职继承完成
- `limit`：**必填**，1~1000
- `owner_filter.userid_list`：最多 100 个群主；**不填则拉应用可见范围内全部群主，可见范围超 1000 人会报 `81017`**
- 返回：`group_chat_list[{chat_id, status}]` + `next_cursor`（空串表示无更多数据）
- 权限：自建应用 secret 获取的 access_token；**群主必须在应用可见范围内**

### 3.3 获取客户群详情 `externalcontact/groupchat/get`

- 请求：`{chat_id, need_name}`（`need_name=1` 时返回成员姓名）
- 返回 `group_chat`：`chat_id` / `name` / `owner`（群主 userid）/ `create_time` / `member_list[{userid, type, join_time, group_nickname, name}]`，`type`：`1` 企业成员 / `2` 外部联系人

### 3.4 创建企业群发 `externalcontact/add_msg_template`（推送主通道）

- 请求：`{chat_type, chat_id_list, sender, text, attachments, allow_select}`
- `chat_type="group"` 表示发给客户群；**`chat_id_list` 仅在 `chat_type=group` 时有效，最多 2000 个群**
- **`sender` 在发送给客户群时必填**（成员 userid，取群主 `owner`）
- 文本：`text.content`（最多 4000 字节）；链接卡片：`attachments[{msgtype:"link", link:{title, url, picurl, desc}}]`（`title` / `url` 必填，`picurl` / `desc` 可选）
- 返回：`{errcode, errmsg, fail_list, msgid}`
  - `fail_list`：无效或无法发送的 external_userid / chat_id 列表
  - **`msgid`：企业群发消息 id，可用于查询发送结果**
- **关键约束：调用该接口不会立即发送消息，需成员（群主）在企业微信客户端确认后才真正发送**
- 频率约束：每个客户群每月最多接收条数为当月天数（可在企微「群发助手-设置群发规则」调整为每周七条或每天一条）；超限时该群不再接收

### 3.5 获取群发发送结果 `externalcontact/get_groupmsg_send_result`

- 请求：`{msgid, userid, limit, cursor}`（`limit` 1~1000）
- 返回 `send_list[{external_userid, chat_id, userid, status, send_time}]`
- `status`：`0` 未发送 / `1` 已发送 / `2` 因客户不是好友发送失败 / `3` 因其他原因发送失败

> 该接口使推送记录的状态可以从「待确认」推进到「已发送 / 失败」，实现推送闭环（见 §6.6）。

## 4. 架构总览

```
前端「群管理」页面 (src/pages/WxGroups)
   │
   ├─ src/services/wx.ts        （鉴权 request 封装）
   └─ /api/wx/*  ← require_hospital_admin
        │
        ├─ services/wxwork_service.py   企微 API 客户端（async httpx）
        │    ├─ access_token：Redis 缓存（TTL 7000s）
        │    ├─ groupchat/list（cursor 分页）
        │    ├─ groupchat/get（群详情）
        │    ├─ add_msg_template（群发）
        │    └─ get_groupmsg_send_result（回写发送结果）
        │
        ├─ 定时任务：lifespan 启动 asyncio 后台循环
        │    └─ 每 WX_SYNC_INTERVAL_HOURS 小时：同步群 + 刷新未决推送状态
        │
        └─ MySQL
             ├─ med_wx_group            群快照（企业级，全局共享）
             ├─ med_wx_group_patient    群-患者绑定（按医院隔离）
             └─ med_wx_message          推送记录（按医院隔离）
```

### 4.1 依赖

**不引入任何新第三方依赖**。异步 HTTP 用已有的 `httpx`，定时任务用标准库 `asyncio`，锁用已有 Redis。

### 4.2 租户隔离决策

- **群快照表不加 `hospital_id`**：企业微信群属于企业维度，全系统共享一份同步结果，同步任务只跑一次。
- **绑定表与消息表加 `hospital_id`**：绑定关系与推送记录属于具体医院的业务数据，与其他租户隔离。
- 绑定唯一约束为 `UNIQUE(hospital_id, group_id)`：**同一医院对同一个群最多绑定一位患者，不同医院互不影响**。

### 4.3 菜单与权限

- `menu_service.MENU_SEED` 在「智能诊疗中心」分组下新增 `wxGroups`（标题「群管理」，图标 `WechatOutlined`，`sort_order=26`，位于 `documents(25)` 与 `entities(27)` 之间）
- `ROLE_MENU_SEED` 中授予 `hospital_admin`（其余角色不授予）
- 前端 `ICONS` 映射补充 `WechatOutlined`；`PageKey` 增加 `wxGroups`
- 全部接口走 `require_hospital_admin`

### 4.4 患者数据源（关键决策）

患者档案当前为前端 mock（`services/mock.ts` 的 `patientRows`，`id` 形如 `P-8842`）。本期**不做患者表后端化**，绑定采用**快照方案**：

- 前端从 mock 患者列表中选择，提交 `patient_id` + `patient_name` 给后端
- 后端只存这两个字段的冗余快照，不校验患者是否存在
- 未来患者后端化后，绑定接口可改为从患者表校验并回填，数据库结构无需变更

### 6.4 同步锁

- Redis `setnx` 键 `wx:sync:lock`，TTL 900s，`finally` 中删除
- `redis_client.py` 新增 `redis_setnx(key, value, ttl) -> bool`
- Redis 不可用（`RedisUnavailable`）时降级为进程内 `asyncio.Lock`，保证单机可用

### 6.5 定时任务（`app/main.py` lifespan）

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    init_db()
    task = asyncio.create_task(_wx_sync_loop()) if settings.wx_sync_enabled else None
    try:
        yield
    finally:
        if task: task.cancel()
```

`_wx_sync_loop()`：
1. 若 `wx_sync_on_startup`，先 `await asyncio.sleep(10)` 再同步一次
2. 循环：`await asyncio.sleep(interval_hours * 3600)` → `sync_groups()` → `refresh_pending_messages()`
3. 每次同步独立开 `SessionLocal()`；异常捕获后记录日志，等待下一个周期（不因单次失败终止循环）

### 6.9 企微错误码映射

| errcode | 含义 | 处理 |
| --- | --- | --- |
| `0` | 成功 | — |
| `40001` / `40014` / `42001` | 凭证无效 / token 过期 | 强制刷新 token 后重试一次；仍失败提示「企微凭证无效，请检查 WX_CONTACT_SECRET」 |
| `48002` | API 未授权 | 提示「自建应用未开通客户联系权限」 |
| `60011` | 无权限访问资源 | 提示「群主不在应用可见范围内」 |
| `81017` | 可见范围超 1000 人 | 提示「请配置 WX_OWNER_USERIDS 缩小拉取范围」 |
| `45009` | 接口调用超过频率限制 | 等待后重试一次；同步场景下跳过该群并记录 |
| `41048` | 群发额度已达上限 | 提示「该群本月接收群发已达上限」（写入 `fail_reason`） |
| 其他 | — | 统一 `WxWorkError`，原文透传 `errmsg` |

## 8. 错误处理与边界

1. **凭证未配置**：所有写入接口返回 503 + 明确引导文案；列表接口返回空列表 + `configured=false`，页面顶部 alert 提示管理员配置 `.env`。
2. **同步并发**：定时同步与手动同步共用同一把锁，冲突返回 409，前端提示「同步进行中」。
3. **群详情拉取失败**：单个群失败不影响整体同步，结果计入 `failed`，同步完成后提示「N 个群同步失败」。
4. **推送失败**：`fail_list` 命中该群 → 记录 `status=fail` 与原因；接口 HTTP 仍返回 200，由前端按记录状态提示（业务失败而非请求失败）。
5. **群主确认超时**：状态长期停留在 `pending` 属正常；定时任务按 §6.5 刷新最近 24 小时内创建的 pending 记录。`status` 不引入超时状态，前端按 `created_at` 超过 7 天仍为 `pending` 时，在标签后追加「已超时未确认」提示。
6. **删除群的保护**：群记录软删；已绑定患者的群不允许删除（本期不提供删除入口，仅保留软删字段）。

## 9. 安全与合规

- 企微凭证只存服务端 `.env`，**不下发前端**；`WxStatusOut` 仅返回 `configured` 布尔值
- `corpsecret` 使用 `SecretStr`，日志中禁止打印完整 token 与 secret（仅打印错误码）
- 患者姓名等数据仅存快照，不落企微侧；推送内容由操作人填写，系统不做内容审计
- 全部接口受 `require_hospital_admin` 约束，绑定与推送操作记录 `operator_id` / `bind_by` 便于追溯

## 10. 测试与验收

### 10.1 无凭证降级（必须首先验证）

未配置 `.env` 时：服务正常启动，列表返回空 + `configured=false`，页面展示引导 alert，不产生异常日志刷屏。

### 10.2 接口自测（curl，沿用项目既有自测方式）

按顺序验证：
1. `GET /api/wx/status` → `configured`
2. `POST /api/wx/groups/sync` → 返回 `total/added/updated/failed`
3. `GET /api/wx/groups` → 分页与 `keyword` / `bound` 筛选
4. `PUT /api/wx/groups/{id}/patient` → 绑定；重复绑定不同患者验证换绑生效
5. `DELETE /api/wx/groups/{id}/patient` → 解绑
6. `POST /api/wx/messages`（text）→ 落库 `pending` + `wx_msgid`
7. `POST /api/wx/messages`（link）→ 同上
8. `POST /api/wx/messages/{id}/refresh` → 群主确认后状态变 `sent`
9. `GET /api/wx/messages` → 记录列表与筛选
10. 并发 `POST /api/wx/groups/sync` 两次 → 第二次返回 409

### 10.3 前端冒烟

登录 → 侧边栏「群管理」可见 → 同步 → 绑定患者 → 推送（文本 / 链接）→ 查看推送记录 → 刷新状态。只需保证编译通过与主流程可点通，不做额外视觉校验。

### 10.4 验收标准

- 群列表数据来自真实企微接口，与企微管理后台一致
- 群与患者绑定关系刷新页面后保持
- 推送任务提交后，群主在企微收到确认提醒；确认后页面状态变为「已发送」
- 未配置凭证时全链路无 500 错误
